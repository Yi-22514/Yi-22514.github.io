大模型应用个人学习总结

学习 Happy-LLM 第七章之后，我对大模型应用的理解从“把问题发给模型”变成了“围绕模型搭建一个可靠系统”。LLM 本身很强，但真实应用里不能只依赖模型裸答。我们还需要评测、检索、工具、记忆、权限和反馈机制，才能让它稳定地解决具体问题。

这一章主要给我建立了三个关键词：模型评测、RAG 和 Agent。

一、模型评测：先知道模型到底行不行

很多时候我们会因为模型回答得流畅，就误以为它答得正确。但大模型的输出具有迷惑性：它可能语气很自信，内容却是错的；也可能在简单问题上表现很好，在专业场景中突然失效。

所以模型评测是应用前必须做的事情。我现在会从几个维度看模型效果：

  • 准确性：答案是否正确。
  • 完整性：是否覆盖问题中的关键点。
  • 一致性：同类问题是否稳定。
  • 安全性：是否会输出不该输出的内容。
  • 时效性：是否能处理最新知识。
  • 成本与延迟：是否适合真实业务使用。

自动指标有用，但不够。对于开放式生成、问答和 Agent 任务，人工评测、案例集评测和线上反馈同样重要。评测不是一次性的，而应该贯穿整个应用迭代过程。

二、RAG：让模型带着资料回答

RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。它解决的是 LLM 的两个典型问题：知识可能过时，以及回答缺少可追溯依据。

我觉得 RAG 的关键不是“把文档塞给模型”这么简单，而是如何把正确的资料、以合适的长度、放到合适的位置。检索结果质量差，模型就会基于错误上下文回答；切分太碎，语义不完整；切分太长，又会浪费上下文窗口。

RAG 的优势是不用重新训练模型，就能让模型利用私有知识库或最新文档。对于个人博客、学习笔记、公司文档问答这类场景，RAG 很实用。

三、RAG 的难点

学完这一章后，我对 RAG 的难点有了更现实的认识。它不是一个固定模板，而是一条需要不断调试的链路。

首先是文档质量。原始资料如果混乱、重复、过期，后面的向量检索也很难救回来。

其次是切分策略。不同文档适合不同 chunk size。有些内容按标题切分更好，有些内容按段落切分更好，有些表格和代码还需要特殊处理。

第三是检索和重排。向量相似度不一定等于答案相关性，所以很多系统会加入 rerank，把粗召回结果重新排序。

最后是生成约束。模型需要被要求基于资料回答、引用来源、无法回答时明确说明不知道。否则 RAG 也可能变成“带着资料幻觉”。

四、Agent：让模型学会使用工具

如果说 RAG 是让模型会查资料，那么 Agent 是让模型会规划和行动。Agent 通常会让 LLM 扮演决策核心，根据目标拆解任务，选择工具，观察工具返回结果，再决定下一步。

我觉得 Agent 的意义在于，它把 LLM 从“文本生成器”扩展成了“任务调度器”。但这也带来新的风险：工具权限、执行错误、循环失控、错误信息传播，都需要系统层面控制。

五、应用系统比单个模型更重要

第七章给我的最大启发是：大模型应用的核心竞争力不只在模型本身，而在系统设计。

一个可用的 LLM 应用至少需要考虑：

  • 数据从哪里来，是否可信。
  • 检索是否能找到真正相关内容。
  • Prompt 是否清楚约束模型行为。
  • 工具调用是否安全可控。
  • 输出是否能被评估和追踪。
  • 用户反馈能否反哺系统优化。

模型是核心发动机，但应用体验来自整套系统。RAG、Agent、评测和监控共同决定了应用是否可靠。

六、我的阶段性理解

学完这一章之后，我对大模型应用有了一个更清醒的认识：不要把所有问题都丢给模型裸答。对于知识密集型任务，用 RAG 给模型补资料；对于需要操作的任务，用 Agent 接工具；对于严肃场景，用评测和人工反馈把质量闭环做起来。

我接下来如果做自己的 LLM 小项目，可能会优先从个人知识库 RAG 入手。因为我的博客和学习笔记已经有不少内容，正好可以尝试构建一个“基于自己笔记问答”的系统。等检索、引用、回答质量稳定之后，再考虑加入工具调用，让它从问答系统逐步变成学习助手。

这一章也让我意识到，大模型应用不是炫技，而是工程。真正有价值的应用，应该让模型在可靠边界内发挥能力，而不是让用户去承担模型不稳定的后果。
