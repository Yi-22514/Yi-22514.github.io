大模型训练实践个人学习总结

学习 Happy-LLM 第六章时，我感觉自己开始从“理解模型结构”进入“理解训练工程”。前面几章更多是在回答模型是什么、结构怎么搭；这一章则是在回答：如果真的要训练或微调一个大模型，数据、框架、显存、并行、日志、保存、评估这些问题该怎么组织。

这也是我对大模型训练最大的重新认识：训练不是一个简单的 model.fit()，而是一套完整工程系统。

一、Transformers 是训练实践的入口

Hugging Face Transformers 的价值不只是提供模型代码。它更像是一个统一接口，把 tokenizer、model、dataset、trainer、generation、checkpoint 等组件串在一起。

对于学习者来说，Transformers 最大的好处是降低了复现门槛。我们不需要从零写每一种模型结构，也不需要重复处理模型加载、权重保存、推理生成这些通用逻辑。只要理解它的几个核心对象，就能开始做预训练、微调和推理实验：

  • AutoTokenizer：负责文本和 token id 的转换。
  • AutoModelForCausalLM：加载因果语言模型。
  • Dataset：组织训练数据。
  • Trainer 或自定义训练循环：管理训练过程。
  • TrainingArguments：集中配置 batch size、学习率、保存策略等。

我觉得这一步的重点不是“会调用 API”，而是理解这些 API 背后对应训练流程中的哪个环节。

二、数据处理比想象中更重要

训练大模型时，数据处理不是简单读文件。它至少包括清洗、去重、格式转换、tokenize、截断、padding、packing、label 构造等步骤。

不同训练阶段的数据格式也不一样。预训练更关注连续文本的 token 流，目标是预测下一个 token；SFT 更关注指令和回答之间的格式，让模型学会按照用户意图输出。

我现在会特别注意两个点：

  1. 输入格式是否和模型的聊天模板一致。
  2. 训练 loss 是否只作用在应该学习的部分。

如果 SFT 时把用户问题、系统提示和回答全部一视同仁地计算 loss，模型可能会学到一些不必要甚至有害的模板行为。因此，数据整理其实直接影响模型最终的使用体验。

三、DeepSpeed 解决的是显存和并行问题

随着模型变大，单卡显存很快不够用。DeepSpeed 的意义就在于把大模型训练中的显存压力拆开处理。

其中最核心的是 ZeRO 优化。普通数据并行中，每张卡都会保存完整的模型参数、梯度和优化器状态，显存浪费很大。ZeRO 会把这些状态切分到不同 GPU 上，从而显著降低单卡显存占用。

我可以这样理解：

  • ZeRO-1：切分优化器状态。
  • ZeRO-2：进一步切分梯度。
  • ZeRO-3：连模型参数也切分。

这让我意识到，大模型训练的难点不只是“算得快”，更是“放得下”。显存管理、通信开销和并行策略，都是训练系统的一部分。

四、PEFT、LoRA 和 QLoRA

全参数微调大模型成本很高，因为所有参数都要参与训练，显存和计算压力都很大。PEFT 的思想是只训练少量新增参数，让大部分原模型权重保持冻结。

LoRA 是最经典的 PEFT 方法之一。它假设权重更新可以用低秩矩阵近似：

$$W’=W+\Delta W=W+BA$$

其中原始权重 $W$ 保持冻结，只训练低秩矩阵 $A$ 和 $B$。这样训练参数量会大幅减少，但仍然可以让模型适配新任务。

QLoRA 则进一步把基座模型量化到更低精度，再配合 LoRA 训练适配参数。它的目标是让更大的模型能在更有限的显存下完成微调。

我对 LoRA 的理解是：它不是重新塑造整个模型，而是在原模型能力上加一层轻量的任务适配。对于个人学习和中小资源场景，它比全参数微调现实得多。

六、我的阶段性理解

这一章让我意识到，训练大模型的门槛并不只在理论，而在工程。模型结构决定了它能学什么，数据决定了它实际学到什么，训练框架决定了它能不能高效稳定地学。

对于我个人学习来说，比较合理的路线应该是：先用 Transformers 跑通一个小模型的 SFT，再尝试 LoRA 微调，之后再理解 DeepSpeed、ZeRO、混合精度和多卡训练。这样不会一开始就被复杂工程淹没，也能一步步把训练系统拼起来。

这一章也给了我一个很实际的判断：不是所有任务都需要全参数训练。很多时候，选择合适的基座模型、准备高质量数据，再用 LoRA 或 QLoRA 做轻量微调，已经是很有性价比的方案。
